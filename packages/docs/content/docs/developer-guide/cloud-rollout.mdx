---
title: Cloud rollout and rollback
description: Safe deployment order for the cloud billing and tracking control planes.
---

The first cloud release is a coordinated control-plane cutover. Migrations
0012–0020 add the billing and v2 tracking control planes without changing the
legacy scheduler contract or synthesizing billing, target-selection, or rollout
rows. Local and white-label installations therefore keep their existing
`enabled_models` and `delay_override_hours` behavior, but old and new cloud web
or worker versions must not overlap during the cutover to migration 0020.

## White-label and local upgrades

The production white-label database must use a planned maintenance cutover,
not a live schema deployment. First deploy and rehearse the white-label-only
compatibility build whose complete membership reconciliation takes one
transaction-scoped advisory lock per user and tolerates the unique membership
index. Both runtime images must carry the
`com.elmohq.elmo.schema-compatibility=0020` attestation. Its worker must publish
readiness only after every handler is registered, remove readiness before a
graceful one-hour drain, and its web and worker images must have working health
checks. Both images must also carry
`com.elmohq.elmo.release-role=white-label-rollback-only`, and the rehearsed
Compose file must set `stop_grace_period: 65m` for both web and worker. Publish
these images only through the dedicated rollback-only workflow, under
unmistakable, immutable rollback-only tags; it must not publish
packages, a product release, a migrator, or a `latest` tag. Run that build on
the old schema before the maintenance window, record both exact image digests,
and retain them as the only approved rollback runtime. Never use this
compatibility worker as a normal target or in cloud mode: it does not consume
or fence the v2 cloud queues. An ordinary pre-cloud image without these
properties is not an approved rollback after migration 0012.

Configure both database URLs before rehearsing either the target or
compatibility runtime. `DATABASE_URL` may use a pooler, but
`DATABASE_URL_UNPOOLED` must be the provider's direct, session-affine PostgreSQL
endpoint. The two URLs must address the same logical database and advisory-lock
scope. A transaction-pooler endpoint—including a pooler host or port 6543—is
rejected for `DATABASE_URL_UNPOOLED`; do not bypass this check. Make any TLS
certificate, key, Unix-socket, secret, or config mounts required by that direct
endpoint available to web, worker, and the exact migrator. The runtime proves
that both URLs reach the same database before it becomes ready, so an absent or
incorrect direct URL fails closed.

Before the window, restore a fresh database backup in an isolated environment
and run this read-only preview. Migration 0012 intentionally keeps the
highest-privilege membership, then the earliest `created_at` and lowest `id`,
and deletes every other row for the same organization and user. Confirm the
preview with the white-label operator before proceeding.

```sql
WITH ranked_members AS (
  SELECT
    id,
    organization_id,
    user_id,
    role,
    created_at,
    row_number() OVER (
      PARTITION BY organization_id, user_id
      ORDER BY
        CASE role
          WHEN 'owner' THEN 0
          WHEN 'admin' THEN 1
          WHEN 'member' THEN 2
          ELSE 3
        END,
        created_at ASC,
        id ASC
    ) AS duplicate_rank,
    count(*) OVER (PARTITION BY organization_id, user_id) AS duplicate_count
  FROM member
)
SELECT
  organization_id,
  user_id,
  id,
  role,
  created_at,
  CASE WHEN duplicate_rank = 1 THEN 'retain' ELSE 'delete' END AS migration_action
FROM ranked_members
WHERE duplicate_count > 1
ORDER BY organization_id, user_id, duplicate_rank;
```

Every final custom or white-label image pipeline must build web, worker, and
the dedicated `migrate` target from the same source commit and pass
`--build-arg ELMO_RELEASE_VERSION=<matching CLI version>` to all three builds.
Before cutover, inspect each result and require both
`com.elmohq.elmo.schema-compatibility=0020` and
`com.elmohq.elmo.release-version=<matching CLI version>`. `elmo upgrade` rejects
a missing or mismatched label, or a migrator from another release, before it
stops the current runtime. Publish and retain immutable digests even when the
deployment Compose file uses version tags.

Pre-pull or build all three final images and both compatibility runtime images. Stop the
compatibility web service and every custom producer first so no new work can be
enqueued. Then send `SIGTERM` to the compatibility worker with at least a
65-minute container stop grace period. The compatibility worker stops polling
before it drains active jobs; do not send `SIGKILL`. After the worker container
has exited, require this query to return no rows before migration:

```sql
SELECT name, count(*) AS active_jobs, min(started_on) AS oldest_started_on
FROM pgboss.job
WHERE state = 'active'
GROUP BY name
ORDER BY name;
```

If the worker does not exit cleanly within the grace period, or exits nonzero,
abort the cutover and investigate the active job rather than migrating. Apply
migrations 0012–0020 while every application process is stopped. Start and
health-check the final worker before starting web. If the final runtime fails,
keep the migrations applied and restart only the retained, digest-pinned
compatibility images; do not restore an ordinary pre-cloud image. Existing
legacy scheduling continues after restart because these migrations do not
create cloud rollout rows for existing brands.

For CLI-managed local Docker installations, `elmo upgrade` adds the direct URL
for its own PostgreSQL service and performs the same prepared maintenance
boundary automatically. An existing local deployment with an external
database must configure `DATABASE_URL_UNPOOLED` and explicitly pass
`--acknowledge-single-deployment` for this one-time boundary; `--yes` does not
acknowledge that operational claim. White-label and cloud deployments cannot
use that exception. The upgrade serializes concurrent invocations,
pre-pulls or builds target images, and records a private resumable checkpoint
bound to the deployment, database, Docker daemon/context, and Compose project.
It preserves which web/worker services and PostgreSQL were running, drains
every currently live worker cleanly, and removes all old web, worker, and base
migrator containers before crossing the schema boundary. It pins the prepared
target config, runs the exact checkpointed migrator, recreates every previously
existing application container from the checkpointed target IDs without
starting it, then starts only the services that were running before cutover. It
makes the target worker healthy before exposing web. A headerless legacy config
is treated as a maintenance upgrade. If the database may have crossed the
cloud schema boundary, automatic rollback is allowed only to exact
checkpointed images carrying the 0020 compatibility attestation; those IDs are
recreated and re-attested before recovery state is removed. Otherwise the
target config and recovery checkpoint remain in place, and the CLI refuses
manual Compose start commands until the same CLI version resumes successfully.
After cutover, retire cached older CLI binaries: `elmo init` is not an upgrade
mechanism, and only the CLI version recorded by an incomplete recovery may
resume it. Do not run the database migrator separately from this cutover.

## Deployment order

1. Back up PostgreSQL and verify restoration before changing production.
2. Prepare Stripe and every cloud runtime variable before starting a worker or
   admitting web traffic:
   - set `DATABASE_URL_UNPOOLED` to the direct endpoint described above and set
     `ELMO_RUNTIME_FENCE_GENERATION=0020` on every cloud web and worker
     deployment, including Vercel or another source-based deployment. Cloud
     startup fails closed when either value is absent;
   - create the catalog prices with the exact lookup keys, amounts, currencies,
     and intervals defined by the application;
   - configure `${APP_URL}/api/auth/stripe/webhook` with
     `STRIPE_WEBHOOK_SECRET`;
   - create a dedicated portal configuration with subscription updates
     disabled, payment-method updates and invoice history enabled, and
     cancellation enabled at the end of the billing period; then set
     `STRIPE_BILLING_PORTAL_CONFIGURATION_ID`;
   - enable Stripe's failed-payment customer emails and Smart Retries as
     described below;
   - set `STRIPE_SECRET_KEY` and validate the price catalog and portal
     configuration. Cloud worker startup rejects a missing Stripe secret.
3. Stop routing requests to every old cloud web instance so no process can
   create an admission or enqueue new cloud work. Let every old cloud worker
   drain all active billing, tracking, and `analyze-brand-cloud-v2` jobs, then
   stop every old cloud web and worker instance. Verify that no old producer or
   consumer remains before continuing. This is the one-time compatibility
   barrier for migration 0020: an old worker cannot maintain the durable
   provider lease added by that migration. Local and white-label deployments
   use the legacy queues and may remain online when they do not share these
   cloud processes.
4. Apply all database migrations through 0020. Do not remove legacy columns,
   queues, or scheduler code.
5. Start only the new worker version that consumes `reconcile-cloud-billing`,
   `dispatch-tracking-v2`, and `process-tracking-task-v2`. Billing reconciliation
   recovers a Stripe command after a process or webhook-delivery failure; a
   pending command fences tracking until its authoritative Stripe state has
   been projected or the command has definitively failed. Tracking consumers
   are inert for brands without an explicit `brand_scheduler_rollouts` row in
   `v2` mode. The worker drains due organization entitlement cursors before
   dispatch, so future custom contract boundaries rebuild only the affected
   workspaces.
   The same cloud-only billing maintenance job confirms and purges expired
   cancellation-retention runs. Do not expose the retention-aware web version
   before migrations 0019–0020 and this worker version are live. Migration 0020
   gives every running brand-analysis provider call a renewable durable lease;
   the retention worker expires only a lost lease before allowing purge.
   Confirm the worker has created and registered the
   `analyze-brand-cloud-v2` consumer before deploying the web sender. That v2
   queue stores only organization/brand IDs, admission generation, and a
   one-way request fingerprint; it resolves the current brand name and website
   behind the provider-start lock instead of persisting customer content in
   pg-boss. Local and white-label workers continue using the legacy
   `analyze-brand` contract.
6. Deploy the new web/control-plane version only after the new worker is the
   exclusive cloud consumer and all of its queues have been verified. Cloud
   requests fail closed until the Stripe readiness check succeeds; non-cloud
   modes do not call that check.
7. Admit only new cloud signups and brands. New cloud brands receive explicit
   v2 tracking policy and rollout rows transactionally. Existing brands with no
   rollout row—including every upgraded local or white-label brand—remain on
   legacy scheduling.

Verify the first cloud brand end to end before increasing traffic: Checkout and
webhook projection, resolved entitlements, target and Claude prompt assignments,
schedule materialization, provider attempts, and usage-bucket accounting.

## Stripe revenue-recovery contract

Stripe owns subscription billing messages and payment recovery. Elmo does not
send a second set of billing emails through Resend. Configure these settings in
both the Stripe sandbox and live account before admitting traffic:

1. Make sure every Elmo organization Customer in Stripe has a deliverable
   billing email. New self-serve Checkout customers receive the verified email
   of the owner or admin who starts Checkout. Audit or correct any Customer
   created before that behavior was deployed; Stripe cannot send recovery mail
   to a Customer without an email.
2. In **Billing → Revenue recovery → Emails**, enable **Send emails when card
   payments fail** and use Stripe's hosted recovery page. Stripe sends the
   failed-payment email and secure payment-update link. Enable payment-
   confirmation emails as well so 3D Secure or similar customer action does not
   silently stall payment. See [Stripe customer
   emails](https://docs.stripe.com/billing/revenue-recovery/customer-emails).
3. In **Billing → Revenue recovery → Retries**, enable Smart Retries. Elmo gives
   a `past_due` subscription exactly seven days of access, so set the maximum
   retry duration to **1 week**, not Stripe's longer default recommendation.
   Choose a deliberate final state (`unpaid` for portal-based manual recovery,
   or `canceled` for a fresh Checkout) rather than leaving the subscription
   indefinitely `past_due`. See [Stripe Smart
   Retries](https://docs.stripe.com/billing/revenue-recovery/smart-retries).
4. Use a dedicated Customer Portal configuration with:
   - payment-method updates enabled;
   - invoice history enabled;
   - subscription cancellation enabled with `at_period_end` mode;
   - subscription plan and quantity updates disabled, because Elmo validates
     capacity and applies those changes through its durable billing commands.

   Cloud startup rejects a portal configuration that violates these settings.
   Stripe emits `customer.subscription.updated` when cancellation is scheduled
   or reversed and `customer.subscription.deleted` when it completes; Elmo
   projects those events into the billing page and access policy. See [Stripe
   portal configuration](https://docs.stripe.com/customer-management/configure-portal)
   and [portal webhook behavior](https://docs.stripe.com/customer-management/integrate-customer-portal).

Stripe normally suppresses automatic customer emails in a sandbox. Use an
address on a verified email domain or belonging to a Stripe team member when
testing, then inspect the Customer's email log and exercise failed payment,
recovery, scheduled cancellation, reactivation, and final cancellation before
launch.

## Cancellation retention and purge

An accepted authoritative terminal subscription projection (`canceled` or
`incomplete_expired`) schedules product data deletion 60 days after Stripe's
actual `ended_at` timestamp. Reversing a scheduled cancellation while the
subscription is still active never starts the clock. A later active, past-due,
or otherwise recoverable subscription cancels the open retention run; the
original run remains as an audit record and cannot be reopened by a stale
webhook. If that recovery instead ends as `incomplete_expired`, its terminal
projection starts a new retention cycle. A failed recovery never makes product
data permanently ineligible for deletion.

Deletion has two durable safety phases. During the final 24 hours the worker
rechecks the complete Stripe Customer subscription list under the
organization's billing/capacity lock and records `confirmed`. Purge cannot run
until both the 60-day boundary and at least one hour after confirmation. It
then repeats the Stripe check under the same lock immediately before the
destructive transaction. An unavailable or ambiguous Stripe response fails
closed, records `last_error`, and leaves all product data intact for retry.
A pending durable billing mutation—including an open or completed recovery
Checkout whose subscription has not yet been projected—also defers both phases
without contacting Stripe or deleting data. An in-flight brand analysis or
tracking provider call defers both phases too, so its result cannot race a
workspace purge.

Use this read-only preview before launch and when investigating a due or failed
run:

```sql
SELECT
  retention.id,
  retention.organization_id,
  retention.status,
  retention.source_subscription_status,
  retention.source_subscription_ended_at,
  retention.eligible_at,
  retention.confirmed_at,
  retention.purge_after,
  retention.check_attempt_count,
  retention.last_checked_at,
  retention.last_error,
  billing.status AS current_billing_status,
  billing.stripe_subscription_id AS current_subscription_id,
  (SELECT count(*) FROM organization_billing_mutations
   WHERE organization_billing_mutations.organization_id = retention.organization_id
     AND organization_billing_mutations.status = 'pending') AS pending_billing_mutations,
  (SELECT count(*) FROM brand_analysis_admissions
   WHERE brand_analysis_admissions.organization_id = retention.organization_id
     AND brand_analysis_admissions.status = 'running') AS running_brand_analyses,
  (SELECT count(*) FROM tracking_provider_attempts
   WHERE tracking_provider_attempts.organization_id = retention.organization_id
     AND tracking_provider_attempts.status = 'started') AS started_provider_attempts,
  (SELECT count(*) FROM brands WHERE brands.organization_id = retention.organization_id) AS brands,
  (SELECT count(*) FROM reports WHERE reports.organization_id = retention.organization_id) AS reports,
  (SELECT count(*) FROM apikey WHERE apikey.reference_id = retention.organization_id) AS api_keys
FROM organization_data_retention_runs AS retention
LEFT JOIN organization_billing_subscriptions AS billing
  ON billing.organization_id = retention.organization_id
WHERE retention.status IN ('scheduled', 'confirmed')
   OR retention.last_error IS NOT NULL
ORDER BY retention.eligible_at;
```

The purge removes organization API keys and organization-owned reports, then
all brand analysis, opportunity, competitor, citation, raw answer, prompt,
target-selection, schedule, occurrence, task, and brand rows. Provider attempts
are retained only as content-free usage/cost audit: task, brand, prompt,
prompt-run, provider-request, and unstructured error fields are detached or
cleared and the attempt is stamped with the retention-run ID. Organization,
membership, user/account, invitation, Stripe subscription/item/mutation,
webhook inbox, custom-contract revision, usage-bucket, and retention audit rows
remain available for accounting and support.

Recovery before purge is automatic after Stripe projects the recovered or
replacement subscription. Verify that the open run becomes `canceled` and that
tracking entitlement reconciliation resumes before telling the customer their
workspace is recovered. A `purged` run is terminal: a later subscription starts
an empty workspace, and product data can only be recovered from a separately
validated backup. Do not manually change a run to `confirmed` or `purged`; fix
the Stripe state or worker error and let the authoritative checks retry.

## Rollback

Stop new cloud signups and Checkout first. For each cloud brand being rolled
back, transactionally change its rollout mode from `v2` to `paused` and
increment its generation before rolling back worker or web containers. Paused
is deliberately owned by neither scheduler: a new cloud brand has no safe
legacy `enabled_models` projection, and sending it to `legacy` could execute
every deployment target without cloud metering. The v2 dispatcher only claims
explicit current-generation v2 work, and task execution rechecks that policy
before a provider call.

```sql
BEGIN;
UPDATE brands
SET enabled_models = ARRAY[]::text[],
    updated_at = now()
WHERE id IN ('verified-cloud-brand-id')
  AND organization_id = 'verified-organization-id'
  AND EXISTS (
    SELECT 1 FROM brand_scheduler_rollouts rollout
    WHERE rollout.brand_id = brands.id AND rollout.mode = 'v2'
  )
RETURNING id, organization_id, enabled_models;

UPDATE brand_scheduler_rollouts
SET mode = 'paused',
    generation = generation + 1,
    last_rolled_back_at = now(),
    updated_at = now()
WHERE brand_id IN ('verified-cloud-brand-id')
  AND mode = 'v2'
RETURNING brand_id, mode, generation;
```

Keep the transaction open and inspect both result sets. Verify that both
statements return the same complete brand-ID set. If they do, commit with a
separate explicit command:

```sql
COMMIT;
```

Otherwise issue `ROLLBACK;` and correct the verified IDs before retrying. Only
then roll back containers. The empty `enabled_models` projection also prevents
provider calls if the previous worker does not recognize `paused`. Never
broaden this update to brands that were not part of the cloud rollout, and
never set a cloud-created v2 brand to `legacy`. Resume it only with the
`resumeCloudTrackingRollouts` operation after restoring a compatible v2 worker;
that operation increments the generation again and makes the organization
entitlement cursor immediately due.

Keep migrations 0012–0020 applied during rollback; reversing them would be the
destructive part of the release. A white-label rollback must use the rehearsed
compatibility image described above because an ordinary pre-cloud membership
writer is not approved after the unique index exists. Stripe retries failed
webhook delivery, so restore a webhook-capable cloud web version before
resuming billing traffic.

This release has no contract migration. Do not remove `enabled_models`,
`delay_override_hours`, the legacy queues, or missing-rollout legacy behavior
until a separately rehearsed release proves every supported deployment has
completed its cutover.
