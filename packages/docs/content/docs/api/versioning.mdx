---
title: Versioning and Deprecation
description: How the Elmo API is versioned and how deprecations are announced.
---

The REST API is versioned in its path: every endpoint lives under `/api/v1`. Changes that would break
existing clients generally go into a new version rather than into `/api/v1`.

## What Can Change Within a Version

Within `/api/v1`, a stable operation usually only gains:

- new endpoints
- new optional request parameters
- new fields in responses
- new values of an error's `code` — treat one you don't recognize as its HTTP status implies

Write clients that ignore fields they don't know.

An operation marked `x-stability: experimental` in the [OpenAPI description](/api/openapi.json) says so
in the first line of its description too. Its response shape may still change.

## How a Deprecation Is Signalled

When a stable operation is deprecated, it is marked `deprecated: true` in the OpenAPI description and
announced in the [changelog](/changelog). Its responses may also carry a `Deprecation` header
([RFC 9745](https://www.rfc-editor.org/rfc/rfc9745)) and, once a removal date is set, a `Sunset` header
([RFC 8594](https://www.rfc-editor.org/rfc/rfc8594)).

## Self-Hosted Instances

A self-hosted instance runs the API of the release it was installed from, so a deprecation reaches it
only when you upgrade. Read the release notes before upgrading.
