---
title: Versioning and Deprecation
description: How the Elmo API is versioned, what may change without notice, and how deprecations are announced.
---

The REST API is versioned in its path: every endpoint lives under `/api/v1`. The version only changes
for a break — something an existing client could trip over — and when it does, the new version ships
alongside the old one rather than replacing it.

## What Can Change Within a Version

Within `/api/v1`, a stable operation only ever gains things:

- new endpoints
- new optional request parameters
- new fields in responses
- new values of an error's `code` — treat one you don't recognize as its HTTP status implies

Write clients that ignore fields they don't know. Nothing is renamed, removed, or retyped in place.

An operation marked `x-stability: experimental` in the [OpenAPI description](/api/openapi.json) says so
in the first line of its description too. Its response shape may still change, and it is outside the
notice period below.

## How a Deprecation Is Signalled

Before a stable operation is removed:

1. It is marked `deprecated: true` in the OpenAPI description.
2. Every response from it carries a `Deprecation` header ([RFC 9745](https://www.rfc-editor.org/rfc/rfc9745))
   giving the date it was deprecated, a `Sunset` header ([RFC 8594](https://www.rfc-editor.org/rfc/rfc8594))
   giving the date it stops working, and a `Link` header with `rel="deprecation"` pointing at the
   migration notes.
3. The deprecation is announced in the [changelog](/changelog).

The sunset date is at least six months after the deprecation date. Until then the operation keeps
working exactly as before.

## Self-Hosted Instances

A self-hosted instance runs the API of the release it was installed from, so a deprecation reaches it
only when you upgrade. Read the release notes before upgrading across a sunset date.
